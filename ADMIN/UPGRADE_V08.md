# Upgrade a compatible campaign to v8.1.1 experimental

Cold ADMIN procedure for a requested program update. v8.1.1 is an incremental instruction update from v0.8.1 and preserves the v0.7.3, v0.8.0 and v0.8.1 save, agreement, archive, person/system and handover formats. It adds a direct-attention baseline trigger to the selective independent-agent procedure and retains the standing fallback. A program-only upgrade creates no save, contract revision, fictional event or new generation permission. Ordinary startup never performs this operation automatically. Existing individual state remains authoritative; do not retroactively initialize past encounters or reroll them during installation.

Use a complete separate upgrade copy. Keep the old campaign and its compatible runtime available throughout; never extract a blank kit over a played campaign. For an older/custom layout, identify and explicitly map its compatibility first through `ADMIN/UPGRADE_V07.md`; do not assume an unexamined format is supported.

## Preserve the starting campaign

1. Check the source's exact `RECOVERY/ACTIVE.md` and `HANDOVER/ACTIVE.md` paths. Reconcile recovery with the compatible old procedure first. Finish, return/import or explicitly cancel a live handover before changing its frozen program dependencies; preserve accepted receiving play. Do not update either side of an active snapshot independently.
2. Use the old runtime to full-save any outstanding accepted play before switching. Verify the save and its real evidence coverage; a source gap must remain labelled. If no unsaved play exists, do not manufacture a save just to upgrade. Record the actual source build, campaign/save/contract identities and evidence boundary.
3. Preserve a restorable complete copy of the old campaign and runtime, including custom files, assets, archives and retained recovery/handover material. Use an explicitly named absent destination and check resolved paths and link boundaries before copying; do not follow a symlink into another workspace. Verify the full copied file/path set and bytes against the source using the host's real operations, recording the method and any limitation. Keep this backup unchanged.
4. Create a separate working upgrade copy from that verified campaign, again refusing an occupied destination. Verify it against the backup before any program replacement. Identify the trusted v8.1.1 release source and exact supplied program files. A published label alone does not prove the files match; retain available commit/package identity and integrity results.

## Select the exact program write set

Compare old and new program files and build an exact manifest of every replacement, addition and proposed removal. Retain locally modified program files for review; do not blindly overwrite a customization merely because its path is normally program-owned. The upgrade request authorizes the compatible program update; ask only about an actual unresolved customization, compatibility conflict or additional behavioral change.

Do not reset NOW, KNOWN, CAST_STATUS, CORRECTIONS, BEARING, PC/person shards, CURRENT_SAVE or CAMPAIGN_CONTRACT. Do not add stance headings, initialize unknown traits, reroll relationships, rename person ids or reinterpret missing historical provenance. The existing agreement continues to govern this campaign, including fixed premises and all actual authorship limits. A valid brief needs no rewrite.

No removal is implicit. If an obsolete program path really needs removal, name it in the reviewed write set and protect its full preimage; keep unknown files. Retained RECOVERY and HANDOVER history is never a cleanup target.

## Apply one protected program update

1. In the upgrade copy, follow `ADMIN/RECOVERY.md` before replacing anything. Record kind `program-upgrade`, source/target build identities, base save/contract ids, the exact file and directory sets, and complete intended target files. Preserve and byte-verify full preimages of every affected existing file, including VERSION and customized text where applicable. Record new-path absence and directory preexistence. Create the active marker before campaign-path mutations.
2. Install only the reviewed program set. Verify each written file against its intended source and inspect the resulting entrypoint/procedure links. Keep CURRENT_SAVE, the agreement and all protected campaign data unchanged. Run checks sequentially after writes, never against a changing tree. A pending recovery-marker finding is expected at this stage and is not a reason to skip other defects.
3. Verify compatibility: same campaign/save/contract ids and revisions, engine/module binding, safety, PC/current-person routes, quantities, private state and archive/evidence boundary. Compare the complete protected campaign path set and bytes to the pre-update manifest, not just the resume summary. Verify custom engine/module references still resolve and no empty template replaced a live record.
4. Verify the installed program files and required new cold route, then publish the intended VERSION last among program replacements. VERSION-last is ordering, not atomicity. Use the target `TOOLS/validate.py` for its structural scope, recording any baseline finding separately from a newly introduced one; inspect current routes and semantic preservation independently. Resolve material incompatibilities or restore while the active marker remains; do not proceed to completion with them outstanding. Structural PASS does not prove lossless interpretation or independent NPC behavior.
5. Complete the recovery record with verified resulting build and unchanged campaign identities. Preserve candidate diagnostics inside that operation, remove only its resolved live staging paths, then remove `RECOVERY/ACTIVE.md` last. After cleanup, run whole-tree structural validation and report its actual result. An unexpected material failure after cleanup keeps PLAY idle and requires a protected repair under RECOVERY before further mutation. Never clear a marker merely to get PASS.

For restoration, use the recorded old program preimages and the exact new-path/directory cleanup rules in RECOVERY. Reverify the old program and unchanged campaign data before marking restored. The untouched full backup remains a separate recovery source; do not claim automatic rollback.

## Resume or change methods prospectively

Report the installed experimental build, upgrade-copy location, unchanged save/contract ids, check results and any actual limitation. Keep the old backup. Start a fresh chat from `OS/AGENTS.md` against the upgrade copy and its existing saved moment. No new-game interview or retrospective NPC reconstruction is required.

v0.8 directs the GM to use existing independent facts within the accepted agreement. Newly unsaved hidden state still has best-effort conversational retention; ordinary PLAY writes no files, private scratch record or automatic establishment checkpoint. Requested full saves/checkpoints retain actual established state through the existing complete-present procedure. An unavailable consequential old value remains a reported source gap.

If the operator also requests a materially different generation/authoring method, use `ADMIN/RECALIBRATE.md` for the prospective agreement change and exact procedure route, preserving unrelated terms. A changed engine or world rule needs its separately reviewed transition; an agreement edit alone does not switch binding or rewrite canon. Keep that optional change distinct from this completed program-only update, without repeating already supplied acceptance. Natural campaign play and optional incident reporting are described in `ADMIN/PLAYTEST_V08.md`.
